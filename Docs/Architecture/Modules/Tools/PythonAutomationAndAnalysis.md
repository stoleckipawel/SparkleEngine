## Target Contract

A future Python tool must have one named workflow and owner rather than a general-purpose scripting layer. It declares interpreter and dependency versions, input/output schemas, deterministic identity, path/root policy, concurrency/resource bounds, exit codes, logs, cancellation, partial-output cleanup, and the exact C++/tool/product consumer. Generated bytes are validated by the owning native consumer; Python does not become a duplicate semantic authority.

Candidate applications include deterministic workload/result analysis, artifact/manifest inspection, bounded data preparation, or reproducible validation orchestration. Runtime Python embedding, editor scripting, and public bindings are separate features and remain unsupported unless they receive their own reachable contract.

## Acceptance Handoff

- `AC-PY-01`: one selected workflow runs from documented clean prerequisites with locked dependencies and deterministic schema/version identity.
- `AC-PY-02`: valid, boundary, malformed, missing, oversized, interrupted, and repeated inputs produce defined outputs, exit status, and cleanup.
- `AC-PY-03`: the native owner validates generated data and no Python/C++ duplicate authority can silently diverge.
- `AC-PY-04`: runtime, memory, input/output volume, and concurrency are bounded and attributable.
- `FM-PY-01`: interpreter/dependency/schema mismatch -> fail before output publication.
- `FM-PY-02`: cancellation or exception -> remove or quarantine partial output and return nonzero.
- `CHK-PY-01`: run twice from frozen inputs and compare manifests/hashes/results; inject malformed, missing, incompatible, and interrupted cases.

These criteria have no candidate results in this documentation pass. [`PY-E01`](../CapabilityEvidencePlan.md#world-content-and-tool-evidence) owns the smallest current-scope proof and negative-claim audit.
