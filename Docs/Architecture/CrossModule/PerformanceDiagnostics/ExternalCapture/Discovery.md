### D05 — Completion Is Still Unproved

The pinned package supplies `PIXSetTargetWindow`, `PIXGpuCaptureNextFrames`, `PIXIsAttachedForGpuCapture`, `PIXEndCapture` and `PIXOpenCaptureInUI`. Its Windows wrappers look up functions in an already loaded capturer. The public [programmatic API](https://devblogs.microsoft.com/pix/programmatic-capture/) describes next-frame scheduling and window delimiters; it does not establish an accessible finalized-artifact notification for this candidate.

The package's disabled `pix3.h` branch includes success-returning no-op wrappers. Compile-time eligibility plus actual attached capturer/activity is mandatory; `SUCCEEDED` alone cannot establish Ready or completion. The inspected open-source `PIXGetCaptureState()` implementation returns zero; no portable busy/finalized interpretation is proven from it. A native capturer could change behavior through its own mechanism, which requires installed-version evidence. Falling busy state, file existence/stable size, completed Present/GPU fence and successful shell open are also rejected as finalization or callback-quiescence oracles.

`PIXEndCapture` is documented for programmatically begun capture, not as an acknowledged cancel/finalize protocol for a scheduled next-frame request. Do not repurpose it. `PIXOpenCaptureInUI` shell-launch success is not confirmed tool inspection or a native handoff completion signal. Whole-process recovery is relaunch; no tested cancellation API is claimed.

**Required next proof:** install/identify the GPU capturer and matching input; inspect its supported API/help/exports; retain a real scheduled capture, a verified completion observation and opened artifact/scene identity; test native hotkey Busy, timeout and shutdown with matching native observations. If that version offers no supportable finalization/quiescence oracle, the programmatic capture cell stays blocked.
